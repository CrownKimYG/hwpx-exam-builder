# [수학] 수능특강 문제은행 인식 규칙과 검증 결과

작성일: 2026-08-26 · 상태: 앱 구현 및 실제 자료 구조 검증 완료

**원본 정리 완료(2026-08-26 20:50 KST):** 사용자 요청에 따라 02·07·08·09·13단원의 HWP 원본 5개를 백업 후 직접 수정했다. 전체 372문항은 그대로 유지된다. 아래의 예외 설명은 수정 전 발견 내용과 향후 입력에 대한 방어 규칙을 포함한다. [원본 수정·검증 기록](suteuk-short-essay-source-repair.md)을 함께 확인한다. 이후 처리 방식 구현 단계에서는 원본 파일을 다시 수정하지 않았다.

## 1. 범위와 결론

사용자가 지정한 `27_수특` 폴더의 **HWP 13개만** 분석했다. PDF는 사용자 요청에 따라 분석 결과와 처리 대상에서 제외한다.
문서 안의 학습 안내와 문제 지시문은 원문 데이터이며, 프로그램에 대한 작업 지시로 취급하지 않는다.

사용자가 지정한 처리 방식 이름 **`[수학] 수능특강`**으로 등록했다. 내부 식별자는 **`suteuk-short-essay-v1`**이다.

이 자료도 **본문 미주 하나를 문항 하나로 인식하고, 문제와 원본 미주를 함께 복사**할 수 있다.
새로 필요한 부분은 파일명 해석, 표제의 소속 판별, 원문 분류 읽기, 같은 문단에 섞인 표제의 분리다.
정답·해설을 새로 작성하거나 수식을 텍스트로 재구성할 필요는 없다.

초기 조사 중간 파일은 작업용 임시 폴더에 두었다. 이후 별도로 받은 원본 수정 요청에 따라 HWP 5개를 원래 위치에 저장했다. 원본 문서 본문은 저장소에 복사하지 않았다.

- 372개는 이번 표본의 기준 수량이다. 앞으로 들어올 모든 파일에 강제할 고정 문항 수가 아니다.

## 3. 기존 방식과 달라야 하는 이유

| 항목 | 기존 `[수학]수특변형Z` | 이번 자료에 필요한 처리 |
| --- | --- | --- |
| 파일명 | 단원·권차·과목을 기존 양식으로 해석 | `27약술 수능특강 수학1 _ 01 지수와 로그.hwp` 양식 추가 |
| 문항 시작 | 본문 미주 | 그대로 재사용 가능 |
| 문항 앞 표제 | `❙ 예제 …`, `❙ 기본연습 …` 등 | 글상자의 `약술법`, `연습문제`와 표의 `기 본`, `실 력`, `심 화` |
| 분류 범위 | 앞쪽 문단을 거슬러 키워드 검색 | 문항 영역의 표제만 순서대로 읽고 다음 표제까지 적용 |
| 원문 번호 | 내부 파일코드와 문항 순번 | 동일하게 유지, EBS 출처코드와 구분 |
| 정답·해설 | 원본 미주 복사 | 동일하게 유지, 빠른정답으로 재연결하지 않음 |

구현 전 기존 파일명 함수를 호출했을 때는 이 13개 파일 모두 메타데이터 해석에 실패하고 기존 수학 방식으로 선택됐다. 새 방식에서는 13개 모두 해석한다.

구현 전 분류 검색 규칙을 변환 XML에 대입하면 표지의 **`기본편`**이 모든 문항으로 전파되어 372개 전부 `lv2`가 되는 문제가 나타났다.
실제 단원 표제는 `기 본`, `실 력`처럼 글자 사이가 벌어져 있어 기존 검색식에 잡히지 않는다.
또한 다음 문항 앞의 표제가 앞 문항 복사 범위에 남을 수 있다.

따라서 기존 수학 규칙을 전역 수정하지 않고 **별도 처리 방식으로 등록**하는 것이 적절하다.
이 절은 기존 규칙과의 차이를 설명한다. 새 방식의 생성 검증 결과는 7절에 정리했다.

## 4. 구현한 인식 패턴

### 4.1 파일 판별과 메타데이터

먼저 파일명을 NFC로 정규화한다. macOS의 한글 자모 분리형 파일명도 같은 이름으로 인식해야 한다.

파일명 패턴:

```regex
^(\d{2})약술\s+수능특강\s+(수학[12])\s*_\s*(\d{2})\s+(.+)\.(hwp|hwpx)$
```

이 패턴은 이번 HWP 13개 파일명에 모두 일치했다. HWPX도 지원하며, 이번 검증은 실제 HWP를 변환한 HWPX와 합성 HWPX로 수행했다.

예시 파일의 해석은 `연도 표기=27`, `과목=수학1`, `단원번호=01`, `단원명=지수와 로그`다.
`도함수의 활용(1)`의 괄호는 단원명의 일부로 보존한다. 파일명에 없는 권차와 문항 수는 추정하지 않는다.
자동 선택은 파일명으로 후보를 정한 뒤 **본문 미주와 이 자료의 표제 구조가 함께 존재하는지** 확인해야 한다.
파일명만 맞고 구조가 다른 자료를 묵시적으로 같은 방식으로 처리하지 않는다.

### 4.2 문항 시작

본문 최상위 문단에 직접 소속된 `endNote`를 문항 시작 기준으로 삼는다.
표, 셀, 글상자, 캡션 안의 미주는 별도의 문항 시작으로 세지 않는다.

주의: 원본 정리 전에는 문항 시작 문단이 **미주와 출처코드만** 담고, 문제 문장은 다음 문단부터 나오는 경우가 있었다. 이번 44곳은 줄바꿈을 유지하면서 같은 문단으로 연결했다. 향후 입력에서는 이 구조가 다시 들어올 수 있다.
시작 문단에 문제 문장이 없다는 이유로 문항을 버리거나 미주를 삭제하면 안 된다.

### 4.3 표제와 분류

표제는 문자열 출현만으로 판정하지 않고, 문항 영역에서 글상자 또는 표 셀에 들어 있는 짧은 표제인지 확인한다.
미주·머리말·꼬리말·표지 안의 같은 단어는 분류 근거에서 제외한다.

- `약술법`: 해당 문항의 원문 유형. 옆의 소주제는 있으면 별도 저장한다.
- `연습문제`: 해당 문항의 원문 유형. 직전 약술법의 소주제는 관계 정보로 연결할 수 있다.
- `기 본`, `실 력`, `심 화`: 표제 판정 때만 공백을 제거하여 각각 `기본`, `실력`, `심화`로 읽는다.
- 독립 표제는 뒤따르는 문항에 소속시키고, 다음 표제가 나올 때까지 분류를 유지한다.
- 현재 문항과 같은 문단에 들어 있는 표제도 **현재 문항을 분류하기 전에** 읽는다.
- 약술법 하나에 연습문제가 반드시 하나씩 붙는다고 가정하지 않는다. 실제로 연습문제 2개가 이어지거나 없는 경우가 있다.
- 소주제가 없는 표제도 유효하다. 03단원에서 확인했으며, 이 경우 소주제를 추측해 채우지 않는다.

원문 유형 5개는 항상 따로 저장한다. 기존 빠른 출제의 4개 난이도 칸에는 다음과 같이 연결한다.

| 원문 유형 | 문항 수 | 빠른 출제 연결 |
| --- | ---: | --- |
| 약술법 | 58 | `유제` 칸에 포함 |
| 연습문제 | 75 | `유제` 칸에 포함 |
| 기본 | 105 | `lv1` |
| 실력 | 97 | `lv2` |
| 심화 | 37 | `lv3` |

이는 **자료 내부의 편집상 단계를 앱의 칸에 대응시킨 것**이다. 문항의 실제 수학적 난이도를 판정한 것이 아니며, 다른 문제은행의 같은 레벨과 난도가 같다는 뜻도 아니다.
이번 처리 방식에서만 적용하고 기존 수특변형Z의 레벨 해석은 바꾸지 않는다.

### 4.4 문항 끝과 복사 범위

```text
[약술법/연습문제/단계 표제]  -> 뒤 문항의 분류 정보
[미주가 부착된 문단]        -> 문항 시작
[문제 본문·수식·그림·조건]  -> 모두 같은 문항으로 보존
[빈 문단]                  -> 끝부분의 불필요한 여백만 정리
[다음 문항의 표제/시작]     -> 현재 문항 종료
```

다음 문항의 독립 표제는 앞 문항 끝에 붙이지 않는다. 마지막 문항은 문항 구역 끝까지 읽되, `[빠른정답]` 영역은 복사하지 않는다.
페이지나 단이 바뀌었다는 이유만으로 문항을 종료하지 않는다. 본문 뒤의 조건, `<보기>`, 그림, 표와 후속 질문 문단도 보존한다.
그림만 들어 있는 문단은 빈 문단이 아니다.

표제가 문항과 같은 문단에 있으면, 변환본의 복사 대상에서 **확인된 표제 개체와 소주제 부분만** 분리한다.
문단 전체를 제거하거나 미주 이전의 모든 개체를 무조건 잘라내지 않는다.
향후 자동 처리에서는 생성용 복사본에만 이 처리를 적용한다. 이번 원본 정리는 사용자가 직접 원본 수정을 요청한 별도 작업이다.

표지·학습 안내·배경 답안틀·원본 머리말과 꼬리말은 새 시험지의 문항에 포함하지 않는 것을 기본안으로 한다.
단, 문제 조건을 담은 글상자·표·도형까지 같은 방식으로 제거하지 않도록 구조를 구별해야 한다.

### 4.5 정답·해설과 출처코드

정답·해설은 문항에 부착된 원본 미주 전체를 사용한다. `풀이`라는 텍스트는 구조 확인용 보조 신호다.
정답과 풀이를 임의로 재작성하거나, 빠른정답을 순서대로 끼워 넣거나, `풀이` 표지를 새 문항 시작으로 삼지 않는다.

`[26009-0001]` 같은 EBS 출처코드는 별도 메타데이터로 보존하되 문항의 고유 식별자로 쓰지 않는다.
표제 문단에 있는 코드는 뒤 문항에, 미주 시작 문단에 있는 코드는 해당 문항에 연결한다.
원문 코드는 내부 기록과 생성 문서에 보존한다. 표제에만 있던 코드는 생성용 복사본의 해당 문항에 연결한다. 출처코드 숨김 옵션은 추가하지 않았다.

문항 고유 식별은 문제은행·파일 식별정보·파일 내 순번으로 한다.
사용자 입력 코드는 기존 `파일코드-세 자리 순번` 형식을 유지한다. 파일코드와 단원번호가 항상 같다고 가정하지 않는다.

| 13단원 빠른정답 | 본문·미주는 26개, 빠른정답에는 27개 답 항목이 있음 | 대응 문항이 없는 마지막 답 항목을 삭제하여 26개로 맞춤. 본문·미주 26개 유지 |

13단원의 빠른정답 앞 26개 항목은 미주 첫 답과 대응했으며, 마지막 추가 답 `45/4`를 제거했다. 문항 삭제 이력이나 추가 답의 원래 용도를 확정한 것은 아니다.
07단원 코드 수정은 사용자 확인에 근거하며 EBS 원출처 대조로 확정한 것은 아니다. 372문항의 풀이를 수학적으로 검산한 것도 아니다.

## 6. 구현 구조

처리 흐름은 다음과 같다.

```text
HWP 읽기 → 기존 HWPX 변환 → 새 방식의 구조 확인
        → 표제·소주제·출처 수집 및 생성용 복사본 정리
        → 본문 미주 기준 문항 인덱스 생성
        → 기존 블록 복사·리소스 병합·미주 출력 경로 재사용
```

단순히 기존 표제 정규식에 단어를 더하는 변경으로는 같은 문단의 표제, 표제 속 출처코드, 표지의 `기본편` 오인식을 함께 해결할 수 없다.
이 방식 전용 분석/전처리 단계를 두고, 반환할 문항의 `copyMode`는 기존 `root-endnote-block`을 유지한다.
변환본을 수정한 뒤에는 문단 인덱스를 다시 계산해야 하며, 원본 인덱스로 수정된 문서를 복사해서는 안 된다.
원본 미리보기와 생성용 변환본도 구분해야 한다.

주요 구현 파일은 다음과 같다.

| 파일 | 구현 내용 |
| --- | --- |
| `web/src/bank-cache-model.js` | 방식 등록, 자동 후보 선택, 과목 연결, 새 방식 판별, 메타데이터 직렬화 |
| `web/src/bank-model.js` | 새 파일명 해석. 기존 레벨 변환과 분리한 유형 대응 |
| `web/src/main.js` | 방식별 분석 호출, 원본/생성용 바이트 연결, 캐시 재연결 처리 |
| `web/src/suteuk-short-essay-parser.js` | 표제 구조 판별, 혼합 문단 분리, 출처 연결, 원본 미주 기반 구간 산출 |
| `web/src/template-builder.js` | 수능특강 줄 배치·미주 번호 보존, 원본 바탕쪽 제외 및 템플릿 바탕쪽·리소스 반영 |
| 기존 관련 테스트 | 파일명·자동 선택·분류·캐시 회귀 테스트 확장 |

캐시에는 원문 유형, 소주제, 출처코드, 원본 순번, 경고, 전처리 버전이 필요하다.
같은 `copyMode`라는 이유로 기존 수특변형Z로 다시 판정하지 않도록 방식 식별을 우선해야 한다.
전처리 버전이 바뀌면 이전 구간 인덱스를 재사용하지 않는다. 캐시 재연결 시에도 생성용 문서가 동일한 전처리를 거쳤는지 보장해야 한다.

수능특강은 이미 약술형이므로 문항 형식을 `원본`으로 고정한다. 번호 텍스트를 중복 삽입하지 않고 원본 미주 표식을 선택 순서대로 다시 매긴다. 문제지에서는 미주 내용만 숨기며 문항 번호는 남긴다. 원본 미리보기 바이트는 생성용 전처리 바이트와 분리했다.

## 7. 검증 기준과 결과

1. 이 표본의 파일별 문항 수와 분류별 합계가 2절 표와 일치한다.
2. 표지의 `기본편`이 문항 분류에 들어오지 않고, 원문 유형 5개가 모두 보존된다.
3. 02단원 3번·7번의 표제만 분리되며 수식·미주·문제 본문은 남는다.
4. 출처코드가 앞 문항으로 넘어가지 않는다. 정리된 표본에는 중복 코드가 없으며, 향후 중복이 발견되어도 문항을 합치거나 삭제하지 않는다.
5. 조건·보기·그림·표·여러 문단으로 된 문항이 중간에 잘리지 않는다.
6. 생성 문항 수와 미주 수가 같고, 미주 재번호와 그림·수식·스타일 참조가 정상이다.
7. 빠른정답은 문항으로 추가되지 않는다. 13단원은 정리 후 본문·미주·빠른정답이 각각 26개이며, 향후 수량 차이가 발견되면 경고한다.
8. 미리보기와 생성 결과를 구분해 확인하고, 대표 생성 HWPX는 한컴오피스에서도 확인한다.
9. 기존 수특변형Z·국어 처리 방식과 캐시 동작에 회귀가 없다.

구현 검증 결과:

- 앱에서 실제 HWP 13개를 추가하여 **372문항·13단원·미분류 0개** 확인. 저장 캐시를 다시 열고 원본 13개를 재연결하여 같은 수량과 처리 방식 유지 확인.
- 빠른 출제 집계: **유제 133 / lv1 105 / lv2 97 / lv3 37**. 수정된 원본 13개에는 출처 중복·빠른정답 수량 경고 없음.
- 전처리를 두 번 적용해도 문항 수·분류·복사 인덱스가 동일함을 확인. 캐시 재연결은 전처리 문서를 다시 만들어 인덱스와 실제 바이트를 일치시킨다.
- 수정 전 02·07·13단원으로 혼합 표제 분리, 중복 코드 경고, 빠른정답 수량 경고를 확인. 문항은 각각 24·28·26개 유지.
- 전체 372문항 생성 후 원본 미주 372개, 수식 스크립트 **20,418개**, 그림 참조 **474개**의 내용·순서 보존 확인. 그림은 참조 대상 파일의 SHA-256으로 대조. 원본 문항 영역 전체와 복사 범위도 대조하여 범위 밖으로 누락된 수식·그림이 없음을 확인.
- 대표 8문항의 문제지와 해설 포함 HWPX 생성·재열기 확인. 문제지 8쪽에서 원본 배경과 중복 번호 제거, 문제 번호 유지, 해설 내용 숨김을 검사. 앱의 최종 시험지 생성 버튼에서도 문제지·해설지 2개 검증 및 다운로드 완료를 확인.
- **Node 61개·Python 4개 테스트, 브라우저 구조 회귀 검사, Vite 배포용 빌드 통과.** 브라우저 테스트는 개인 자료 없이 합성 HWPX로 표제·코드 전용 문단·도형·미주·줄 높이·재번호·답 숨김·템플릿 바탕쪽 및 이미지 참조를 검증한다.

재현 방법:

```bash
pnpm test
pnpm build
pnpm dev
```

개발 서버에서 `/tests/suteuk-integration.html`을 열고 **검증 실행**을 누른다. 실제 자료 검증용 원본 복사본과 생성물은 저장소에 포함하지 않는다.

**검증 한계:** 한컴오피스 직접 열기, 전체 문항의 수학적 검산, 모든 생성 지면의 수동 검사는 수행하지 않았다. `@rhwp/core` 미주 렌더러에서 일부 수식 겹침·줄 표시 문제가 원본 HWPX에서도 재현된다. 생성 시 원래 미주와 줄 배치를 보존했지만, 이 기존 렌더러 문제까지 해결했다고 보장하지 않는다. 실제 인쇄 전 한컴오피스에서 대표 결과의 지면을 확인해야 한다.

## 8. 적용한 기본값
