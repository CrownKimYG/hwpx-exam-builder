## 방법과 범위

- 실제 브라우저: QA 은행이 있는 `127.0.0.1:5174`에서 같은 작업을 세 탭으로 열어 저장 충돌 확인.
- 모듈 진단: 합성 HWPX, 손상 입력, 저장소·네트워크 실패 주입, SVG 필터 확인. 실제 사용자 저장소의 용량을 채우거나 손상시키지 않았다.
- 성능: 로컬 Node + jsdom에서 100·300·600문항 분석 시간과 타이머 지연 측정. **실제 브라우저 렌더링 시간·모바일 성능 측정값은 아니다.**
- 의존성: `pnpm audit --json`, Python `pip check`.
- 배포: 로컬 프로덕션 빌드, 생성 자산, 워크플로와 의존성 고정 방식 검토. 원격 CI나 실제 배포는 실행하지 않았다.

재현 명령:

```sh
pnpm exec node --expose-gc scripts/qa-nonfunctional.mjs
pnpm audit --json
pnpm build
.venv/bin/python -m pip check
```

진단 스크립트는 결과를 출력하는 도구이며, 출력이 발생하거나 프로세스가 정상 종료했다고 결함이 해결된 것은 아니다. 실패 주입은 가짜 IndexedDB 및 추출한 원본 함수의 VM 실행으로 수행한다. SVG 검사는 외부 네트워크나 스크립트를 실행하지 않는다.

## 발견 사항

### NFR-01 · P1 · 데이터 무결성 — 오래된 탭이 최신 작업을 조용히 덮어씀

1. A·B 탭에서 같은 저장 작업을 복원한다.
2. A에서 첫 시험지 제목을 `QA 새 제목 A`로 변경한다. `작업 자동 저장됨`을 확인한다.
3. B에서 원본 미리보기의 다음 페이지만 누른다.
4. 새 C 탭에서 작업을 복원한다.

실제 결과: C에는 변경 전 `시험지01`이 나타난다. 충돌 경고는 없고 B에도 자동 저장 완료가 표시된다. 제목 편집을 하지 않은 미리보기 조작만으로 최신 편집이 사라졌다.

원인: `web/src/main.js:583–600`, `:2393–2394`. 모든 탭이 같은 저장 키를 사용하고, 문서의 모든 click/input/change 및 pagehide에서 자신의 전체 상태를 덮어쓴다. 작업 버전 비교나 다른 탭 변경 감지가 없다. 출제 이력용 잠금은 별도로 존재하지만 작업 초안 충돌은 막지 못한다.

권장: 작업 단위 ID·revision을 저장하고 오래된 revision의 덮어쓰기를 차단한다. 다른 탭의 변경을 알리고, 실제 데이터 변경에만 자동 저장을 수행한다. 잠금만 추가하면 오래된 데이터도 순서대로 저장될 수 있으므로 버전 검사가 함께 필요하다.

완료 기준: A 편집 후 B의 미리보기 이동·탭 닫기·설정 펼치기가 A의 저장 내용을 변경하지 않는다. 동시 편집 시 충돌이나 재불러오기 선택을 제공한다.

### NFR-02 · P2 · 장애 복구 — IndexedDB 연결 실패가 같은 페이지에서 고착됨

- 진단 결과: 조회 2회에 실제 `indexedDB.open` 호출은 1회. 두 조회가 같은 첫 오류로 실패.
- 원인: `web/src/bank-cache.js:33–54`에서 거절된 `databasePromise`를 계속 보관.
- 영향: 일시적 열기 실패 후 환경이 회복돼도 페이지 안에서 다시 은행을 읽으려 하면 연결을 재시도하지 않음. 새로고침이 필요할 수 있다.
- 권장: 연결 실패 시 캐시된 promise를 초기화하고, 닫히거나 버전이 변경된 연결의 수명도 처리한다.
- 검증 수준: 모듈 실패 주입 재현. 실제 디스크 부족·브라우저 DB 장애는 유발하지 않았다.

### NFR-03 · P2 · 장애 복구 — 기본 템플릿 다운로드 실패 후 재시도 불가

- 진단 결과: 첫 fetch를 실패시키고 다음 fetch는 성공하도록 설정했으나, 함수 2회 호출에 fetch는 1회뿐. 두 번째도 첫 오류로 실패.
- 원인: `web/src/main.js:1863–1870`에서 실패한 `templateState.defaultPromise`를 초기화하지 않음.
- 영향: 첫 출력 시 일시적 통신 실패가 발생하면 연결 회복 후 다운로드 버튼을 다시 눌러도 기본 템플릿을 가져오지 못함.
- 권장: 실패 시 promise를 비우고 사용자 재시도에서 다시 요청. 성공한 템플릿만 지속 재사용한다.
- 검증 수준: 원본 함수 그대로 추출한 VM 테스트. 브라우저의 실제 오프라인 상태를 변경하지 않았다.

### NFR-04 · P2 · 성능·응답성 — 문항 분석에 반복 전체 탐색과 긴 동기 작업

최종 측정값:

| 합성 문항 수 | 압축 입력 크기 | 분석 시간 | 최대 타이머 간격 |
| --- | ---: | ---: | ---: |
| 100 | 1,236 B | 169 ms | 169 ms |
| 300 | 3,034 B | 673 ms | 673 ms |
| 600 | 5,779 B | 2,424 ms | 2,424 ms |

600문항은 앞선 두 실행에서도 약 2,368·2,372ms였다. 모두 단순 텍스트·미주만 있는 합성 입력이다. 측정값은 Node + jsdom의 결과이며 실제 브라우저의 시간으로 일반화하지 않는다.

원인: `web/src/parser.js:106–110`, `:258–259`, `:294`. 문항마다 전체 children의 내용 여부를 다시 계산하고 난이도 표식을 뒤로 탐색한다. 문항 수 증가에 따라 반복량이 크게 늘어난다. 앱은 이 파서를 UI 스레드에서 호출하며 파일 사이에서만 실행을 양보한다.

영향: 큰 파일 분석 중 입력·진행 안내·취소 반응이 늦어질 위험. 함수가 async라는 사실만으로 내부 동기 반복이 분리되지는 않는다.

권장: 문단별 내용·난이도 상태를 한 번 계산해 재사용하고, 대용량 분석은 Worker나 분할 실행으로 옮긴다. 실제 대상 기기에서 응답성 예산을 정해 회귀 검사한다.

메모리: 최종 실행의 분석 전후 heap 차이는 29·70·36MiB였다. GC 시점과 JIT 영향이 있어 피크나 누수로 해석할 수 없다. 이번 결과만으로 메모리 누수를 판정하지 않는다.

### NFR-05 · P2 · 자원 보호 — 압축 크기 제한보다 압축 해제가 먼저 실행됨

- 위치: `web/src/parser.js:219–223`; 국어·수능특강 파서도 유사한 순서.
- 앱은 `JSZip.loadAsync(..., {checkCRC32:true})` 완료 후에 256MiB 제한을 확인한다.
- 설치된 JSZip의 `lib/load.js:14–27`, `:50–59`는 CRC 검사를 위해 각 엔트리의 압축을 먼저 해제한다.
- 안전한 재현: 실제 데이터는 작은 파일로 유지하고 중앙 디렉터리의 크기 표시만 256MiB 초과로 변경. 앱의 크기 초과 오류보다 `Bug : uncompressed data size mismatch`가 먼저 발생했다. 대용량 압축 폭탄이나 메모리 고갈은 실행하지 않았다.
- 추가 검토: `web/src/main.js:1900–1916`의 인계 ZIP 경로는 엔트리 수·총 압축 해제 크기 제한 없이 내부 HWPX를 배열에 보관한다.

영향: 제한이 있더라도 그 전에 CPU와 자원이 소비될 수 있고, 인계 ZIP에서는 누적 크기 보호가 부족하다.

권장: CRC 검사를 위한 압축 해제 전에 입력 크기·엔트리 수·예상 총 크기를 확인하고, 실제 해제 과정에도 누적 제한·중단 처리를 적용한다. 메타데이터만 신뢰하는 한 단계 검사로 끝내지 않는다.

## 보강·추가 검증 항목

### SVG 필터의 외부 CSS 참조 처리

`web/src/main.js:775–794`의 실제 필터에 합성 SVG를 넣어 확인했다.

- script, foreignObject, onload, 외부 image href는 제거됨.
- style 요소의 외부 `@import`와 style 속성의 외부 `url(...)`는 남음.

방어 경계의 누락이지만 **실제 HWP/HWPX → WASM 렌더러 → SVG 경로로 이 입력을 만들 수 있는지는 확인하지 않았다.** 따라서 파일 기반 XSS나 개인정보 유출이 재현됐다고 판정하지 않는다. 허용 SVG 요소·속성 및 CSS URL 정책을 정리하고 렌더러 출력과 연결해 검증할 필요가 있다.

### 설치 재현성과 배포 추적성

- Python `requirements.txt`는 python-hwpx 버전이 고정되지 않고, 다른 패키지도 범위 지정이다. 이번 설치의 일관성 검사 통과와 미래의 동일 설치 결과는 별개다.
- 프로덕션 빌드는 성공했고 JS/CSS/WASM 파일명은 해시를 포함한다. 배포 입력은 `web/dist`로 제한된다.
- `deploy-version.txt`는 `subject-handoff-v1`이라는 고정 문자열이라 실제 커밋 판별 정보가 아니다.
- Python 의존성 고정, 빌드 시 커밋 정보 기록을 검토할 수 있다. 원격 배포가 실패한다고 재현한 것은 아니다.
